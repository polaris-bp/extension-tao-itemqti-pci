## 1. アーキテクチャ概要

### 1.1 アーキテクチャスタイル

Math Entry Interaction PCIは、**コンポーネントベース・イベント駆動アーキテクチャ**を採用している。

**主な特徴：**
- モジュール間の疎結合
- イベントによる非同期通信
- 状態管理パターン（State Pattern）の採用
- MVC風の責務分離

### 1.2 システムレイヤー構成

```
┌─────────────────────────────────────────┐
│     ユーザーインターフェース層          │
│  (MathQuill Editor + Toolbar)           │
└─────────────────────────────────────────┘
              ↕
┌─────────────────────────────────────────┐
│      プレゼンテーション層               │
│  (Runtime Controller / Creator Widget)  │
└─────────────────────────────────────────┘
              ↕
┌─────────────────────────────────────────┐
│      ビジネスロジック層                 │
│  (State Management / Response Manager)  │
└─────────────────────────────────────────┘
              ↕
┌─────────────────────────────────────────┐
│      データアクセス層                   │
│  (QTI Response Declaration)             │
└─────────────────────────────────────────┘
```

### 2.2 Runtime モードのコンポーネント

#### 2.2.1 mathEntryInteractionFactory

**責務：**
- PCIインスタンスの生成と初期化
- ユーザーインターフェースのレンダリング
- イベントハンドリング
- レスポンスの管理

**主要メソッド：**

| メソッド | 説明 |
|---------|------|
| `initialize(dom, config, responsesManager)` | PCI初期化 |
| `render(config)` | UIレンダリング |
| `postRender()` | レンダリング後処理 |
| `createMathEditable()` | 編集可能な数式フィールド作成 |
| `createMathStatic()` | 静的数式フィールド作成（Gap用） |
| `getResponse()` | 受験者の回答取得 |
| `setResponse(response)` | 回答の設定 |
| `resetResponse()` | 回答のリセット |
| `destroy()` | リソースのクリーンアップ |

#### 2.2.2 responsesManagerFactory

**責務：**
- 複数の回答入力フィールドの管理
- アクティブな入力フィールドの追跡

**データ構造：**
```javascript
Map {
  'answer-0': {
    input: DOMElement,
    response: { base: { string: 'latex...' } }
  },
  'answer-1': {
    input: DOMElement,
    response: { base: { string: 'latex...' } }
  }
}
```

#### 2.2.3 ToolbarManager

**責務：**
- ツールバーUIの生成
- ツールボタンの有効/無効制御
- ボタンクリックイベントの処理

**ツールグループ：**
- functions（関数）
- symbols（記号）
- geometry（幾何）
- trigo（三角関数）
- comparison（比較演算子）
- operands（演算子）
- matrix（行列）

### 2.3 Creator モードのコンポーネント

#### 2.3.1 Widget (creator/widget/Widget.js)

**責務：**
- Creator環境でのウィジェット初期化
- 状態管理システムの登録
- コンテキスト情報の設定

#### 2.3.2 State Manager

Creator モードでは、**State Pattern**を採用し、編集フェーズごとに異なる状態クラスを使用する。

**状態遷移図：**

```
        ┌──────────┐
        │  Sleep   │ (非アクティブ)
        └──────────┘
             ↓
        ┌──────────┐
   ┌───→│ Question │←────┐
   │    └──────────┘     │
   │         ↓           │
   │    ┌──────────┐     │
   │    │ Correct  │     │
   │    └──────────┘     │
   │         ↓           │
   │    ┌──────────┐     │
   └────│   Map    │─────┘
        └──────────┘
```

##### Question State (states/Question.js)

**責務：**
- 問題プロンプトの編集
- プロパティフォームの管理
- ツールバー設定の変更
- Gap Expression の作成

**主要機能：**
- プロパティフォームの初期化
- ツールバーのカスタマイズ（個別ツールの有効/無効）
- Gap モードの切り替え
- "Add Gap" ボタンの制御

##### Correct State (states/Correct.js)

**責務：**
- Map状態への遷移制御

**動作：**
- レスポンステンプレートを `MAP_RESPONSE` に設定
- 即座に Map 状態に遷移

##### Map State (states/Map.js)

**責務：**
- 正解の定義と管理
- 複数の代替正解の追加・削除
- スコアリング設定
- マッピングルールの管理

**主要機能：**
- 正解回答入力フィールドの管理
- 代替回答の追加
- 各回答へのスコア割り当て
- デフォルトスコアの設定
- スコアの上限・下限設定

## 3. データフローアーキテクチャ

### 3.1 Runtime モードのデータフロー

#### 3.1.1 初期化フロー

```
getInstance()
    ↓
responsesManagerFactory() → responsesManager (Map)
    ↓
mathEntryInteractionFactory()
    ↓
initialize(dom, config, responsesManager)
    ↓
initConfig(config) → this.config
    ↓
render(config)
    ↓
[条件分岐: Gap Mode / Normal Mode]
    ↓
createMathEditable() or createMathStatic()
    ↓
createToolbar()
    ↓
addToolbarListeners()
    ↓
postRender()
    ↓
config.onready(pciInstance)
```

#### 3.1.2 ユーザー入力フロー

**通常モード：**
```
ユーザー入力
    ↓
MathQuill onChange handler
    ↓
trigger('responseChange', [latex, index])
    ↓
responsesManager.set(index, {response: latex})
    ↓
[保存完了]
```

**Gap モード：**
```
ユーザー入力（Gap内）
    ↓
Gap MathQuill field onChange
    ↓
trigger('responseChange', [latex, index])
    ↓
getGapFields() → 全Gapの値を収集
    ↓
カンマ区切り文字列に結合
    ↓
responsesManager.set(index, {response: gapValues})
    ↓
[保存完了]
```

#### 3.1.3 ツールバーボタンクリックフロー

```
ツールバーボタンクリック
    ↓
toolbar mousedown event
    ↓
data-fn, data-latex 属性を取得
    ↓
insertLatex(latex, fn)
    ↓
getActiveMathField()
    ↓
[Gap Mode: gapFields[activeIndex] / Normal: mathField]
    ↓
mathField[fn](latex) // 'cmd' or 'write'
    ↓
mathField.focus()
```

### 3.2 Creator モードのデータフロー

#### 3.2.1 プロパティ変更フロー

```
プロパティフォーム変更
    ↓
formElement changeCallback
    ↓
interaction.prop(name, value)
    ↓
interaction.triggerPci('configChange', [properties])
    ↓
pciInstance.on('configChange', handler)
    ↓
mathEntryInteraction.render(properties)
    ↓
UIが再レンダリングされる
```

#### 3.2.2 正解設定フロー（Map State）

```
Map State 初期化
    ↓
initGlobalVariables()
    ├─ responsesManager を取得
    ├─ 既存のレスポンスをクリア
    └─ gapTemplate を保存
    ↓
initForm()
    ├─ responseForm テンプレートをレンダリング
    ├─ min/max コンポーネント初期化
    └─ 既存の正解データをロード
    ↓
initResponseForm()
    ├─ 既存の正解を取得
    ├─ responsesManager に設定
    └─ UI フィールドを初期化
    ↓
[ユーザーが正解を入力]
    ↓
responseChange イベント
    ↓
responsesManager.set(index, {response: latex})
    ↓
[ユーザーが代替回答を追加]
    ↓
addAlternativeInput()
    ├─ 新しい UID 生成
    ├─ テンプレートを挿入
    ├─ triggerPci('addAlternative', [latex, gapValues, id])
    └─ responsesManager に追加
    ↓
[State 終了時]
    ↓
saveAnswers()
    ├─ responseDeclaration.clearMapEntries()
    ├─ responsesManager から全回答を取得
    ├─ ambiguousSymbols で正規化
    ├─ responseDeclaration.setMapEntry(answer, score)
    └─ responseDeclaration.setCorrect(firstAnswer)
```

#### 3.2.3 Gap 追加フロー

```
"Add Gap" ボタンクリック
    ↓
interaction.triggerPci('addGap')
    ↓
pciInstance.on('addGap', handler)
    ↓
addGap()
    ↓
insertLatex('\\embed{gap}', 'write')
    ↓
mathField.write('\\embed{gap}')
    ↓
MathQuill onChange
    ↓
interaction.prop('gapExpression', latex)
    ↓
[gapExpression が更新される]
```

## 4. イベント駆動アーキテクチャ

### 4.1 イベントフロー

Math Entry Interaction PCI は、**カスタムイベントシステム**を使用してコンポーネント間の通信を行う。

#### 4.1.1 PCI カスタムイベント

| イベント名 | 発火元 | 購読者 | パラメータ | 用途 |
|-----------|-------|-------|-----------|------|
| `configChange` | Creator Widget | Runtime Controller | `[properties]` | 設定変更時の再レンダリング |
| `responseChange` | MathQuill Handler | Map State | `[latex, index]` | 回答変更の通知 |
| `addGap` | Add Gap Button | Runtime Controller | `[]` | Gapの追加 |
| `addAlternative` | Add Alternative Button | Runtime Controller | `[latex, gapValues, id]` | 代替回答の追加 |
| `latexInput` | Map State | Runtime Controller | `[latex, index]` | LaTeX入力の設定 |
| `latexGapInput` | Map State | Runtime Controller | `[gapLatex, index]` | Gap LaTeX入力の設定 |
| `deleteInput` | Delete Button | Map State | `[inputId]` | 入力フィールドの削除 |

#### 4.1.2 イベント実装

**イベント登録：**
```javascript
// PCI インスタンスにイベントマネージャを追加
event.addEventMgr(pciInstance);

// イベント購読
pciInstance.on('eventName', function(param1, param2) {
    // ハンドラ処理
});
```

**イベント発火：**
```javascript
// Creator側からRuntimeへ
interaction.triggerPci('eventName', [param1, param2]);

// Runtime側
pciInstance.trigger('eventName', [param1, param2]);
```

### 4.2 イベントライフサイクル

```
[Component A]
    |
    | 1. trigger/triggerPci
    ↓
[Event Manager]
    |
    | 2. dispatch to handlers
    ↓
[Component B Handler]
    |
    | 3. process event
    ↓
[Component B]
    |
    | 4. optionally trigger new events
    ↓
[Event Manager]
```

## 6. 設計パターン

### 6.1 使用されている設計パターン

#### 6.1.1 Factory Pattern

**使用箇所：**
- `mathEntryInteractionFactory()`
- `responsesManagerFactory()`

**目的：**
- インスタンスの生成ロジックをカプセル化
- 初期化処理の一元管理

#### 6.1.2 State Pattern

**使用箇所：**
- Creator Widget States (Question, Correct, Map)

**目的：**
- 編集フェーズに応じた振る舞いの変更
- 状態遷移の明示的な管理

#### 6.1.3 Observer Pattern (Pub/Sub)

**使用箇所：**
- PCI イベントシステム

**目的：**
- コンポーネント間の疎結合
- イベント駆動の非同期処理

#### 6.1.4 Template Method Pattern

**使用箇所：**
- State クラスの `init()` / `exit()` メソッド

**目的：**
- 共通の初期化・終了処理フローの定義
- サブクラスでの拡張ポイントの提供

#### 6.1.5 Strategy Pattern

**使用箇所：**
- MathQuill の `cmd` vs `write` 挿入戦略

**目的：**
- LaTeX挿入方法の動的な切り替え

## 7. レンダリングモード判定ロジック

### 7.1 レンダリングモード決定木

```
render(config)
    |
    ├─ inGapMode() && inQtiCreator() && inResponseState()
    │   → createMathStatic() (静的数式 + 編集可能Gap)
    │   → monitorActiveGapField()
    │   → toggleResponseCorrectRow(true)
    │
    ├─ inGapMode() && inQtiCreator() && !inResponseState()
    │   → createMathEditable(true) (Gap追加可能な編集モード)
    │   → setLatex(gapExpression)
    │
    ├─ !inGapMode() && inQtiCreator() && !inResponseState()
    │   → createMathStatic() + togglePlaceholder(true)
    │   → (プレビュー表示)
    │
    ├─ !inGapMode() && inQtiCreator() && inResponseState()
    │   → createMathEditable(true) (正解入力モード)
    │   → toggleResponseCorrectRow(true)
    │
    ├─ isReviewMode && !inGapMode()
    │   → createMathStatic() (読み取り専用)
    │
    ├─ isReviewMode && inGapMode()
    │   → createMathStatic() + setGapsDisabled(true)
    │   → hideCursors()
    │
    ├─ inGapMode() && !inResponseState()
    │   → createMathStatic() (受験者用Gap問題)
    │   → monitorActiveGapField()
    │
    └─ else (通常の受験者モード)
        → createMathEditable(false)
```

### 7.2 モード判定メソッド

| メソッド | 条件 | 説明 |
|---------|------|------|
| `inQtiCreator()` | `$container.hasClass('tao-qti-creator-context')` | Creator環境かどうか |
| `inGapMode()` | `config.useGapExpression === true` | Gap Expressionモードかどうか |
| `inResponseState()` | `config.inResponseState === true` | 正解入力状態かどうか |
| `inJapanese()` | `userLanguage === 'ja'` | 日本語ロケールかどうか |

## 8. パフォーマンス最適化

### 8.1 最適化戦略

#### 8.1.1 DOM操作の最適化

- イベントデリゲーション（ツールバーボタン）
- WeakMap を使用したキャッシュ（自動折り返し処理）
- 必要時のみ再レンダリング

#### 8.1.2 メモリ管理

- `destroy()` メソッドでのリスナー解除
- MathQuill インスタンスの `revert()` 呼び出し
- WeakMap の使用（GC対象）

#### 8.1.3 計算の最適化

- `getWidth()` での `getBoundingClientRect()` 使用（jQueryよりも高速）
- 幅計算のキャッシング（自動折り返し）

## 9. エラーハンドリング戦略

### 9.1 エラー処理方針

- **防御的プログラミング**: `toBoolean()` での undefined チェック
- **フォールバック**: デフォルト値の使用
- **検証**: `_.isFunction()` でのメソッド存在チェック

### 9.2 エラー発生ポイント

| ポイント | 対策 |
|---------|------|
| 初期化時の設定値 | `toBoolean(value, defaultValue)` |
| MathQuill API呼び出し | メソッド存在チェック |
| DOM要素アクセス | 要素存在チェック |
| イベントハンドラ | try-catch（実装推奨） |

```javascript
states.custom = CustomState;
```

## 12. 技術的負債

### 12.1 既知の課題

| 項目 | 内容 | 優先度 |
|------|------|--------|
| MathQuill API | 実験的APIの使用 (`registerEmbed`) | 中 |
| 自動折り返し | パフォーマンス最適化の余地あり | 低 |
| アクセシビリティ | スクリーンリーダー対応が不完全 | 高 |
| テストカバレッジ | ユニットテストが不足 | 中 |

### 12.2 リファクタリング候補

- ツールバー管理の分離（独立モジュール化）
- 状態管理ロジックの簡素化
- レンダリングモード判定の簡略化
